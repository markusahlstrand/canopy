# S12a #14: legacy WebDAV "Shared with me" acceptance

Covers the four remaining boxes of [#14](https://github.com/markusahlstrand/canopy/issues/14) for the **legacy `apps/api` endpoint only**. The Substrat drive vertical is accepted separately in [s12a-299](s12a-299.md).

## What was tested

- **Endpoint:** the legacy Hono app (`createApp`) served by `@hono/node-server` on a real loopback TCP port (`http://127.0.0.1:<ephemeral>/dav`), with an in-memory libsql store. Not a deployed install.
- **Client:** the [`webdav`](https://www.npmjs.com/package/webdav) package (v5), a real WebDAV client sending PROPFIND, GET, PUT, MKCOL and DELETE with HTTP Basic app-password auth. It is not Finder, Windows Explorer or rclone.
- **Test:** `apps/api/src/webdav-client-acceptance.test.ts`. It sits beside the existing in-process `webdav-shared-folders.test.ts`, which stays.

## Results (14 October 2026)

| #14 box | Result |
| --- | --- |
| A direct grant appears, opens its subtree, and respects viewer vs editor rights | Pass. A viewer sees `Shared with me/<folder> [<sha256>]`, lists and reads the subtree, and gets 403 on PUT, MKCOL and DELETE. A `..` escape to a sibling folder answers 404. An editor can PUT inside the mount, and the owner sees the file. Nothing is writable at the virtual root. |
| Revocation removes access, including an old mount URL | Pass. After the grant is withdrawn, GET of a file through the old URL answers 404 and `Shared with me` leaves the root listing. |
| Colliding folder names and a personal `Shared with me` folder stay distinct | Pass. Two grants both named `Photos` get two mounts with different URL names. A personal `Shared with me` folder keeps its own contents, and the virtual root moves to `Shared with me (Canopy 1)`. |
| Record the endpoint, client and results | This file. |

## Observations

- The URL segment of a mount is `<label> [<full sha256>]`. The readable `<label> — <space> [<8 hex>]` is only the `displayname` property, so a client shows the long name unless it reads that property.
- After revocation, PROPFIND on the old mount URL answers 207 with an empty listing instead of 404. The virtual root is gone, so the URL is an ordinary missing personal path, and this endpoint answers 207 empty for any missing folder. No revoked content is exposed. It is a legacy quirk and was left as it is.
