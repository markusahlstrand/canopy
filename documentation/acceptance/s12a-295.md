# S12a #295: Plugin install and runtime

Parent: [#78](https://github.com/markusahlstrand/canopy/issues/78).

## Behavior and corrections

A failed sandbox can retry in a fresh frame. Native iframe interaction is blocked while a save is pending; a successful save produces a new file version, which remounts the editor on the accepted bytes. Reviewing the same catalog artifact again resets capability approval; source, manifest and audience edits reset it immediately. A signed GitHub import keeps its server-attested provenance even when its bytes match a bundled catalog entry.

## Real-browser evidence

On 9 October 2026, `e2e/plugins.spec.ts` passed eight cases across isolated Chromium desktop and mobile projects. The built SPA, real Worker, OIDC login, real stores and plugin bridge handle accepted operations. The public GitHub import fetches the real repository at pinned ref `e192c2c`; an ephemeral local router secret enables real signed import tokens. Only the explicit byte-failure and delayed-save cases intercept transport. No production account or browser profile is used.

## npm import fixture (local)

`examples/npm/canopy-plugin-sample` is a compatible npm package (`canopy-plugin-sample`: manifest under `package.json#canopy`, self-contained ES module entry). The browser harness packs it with the real `npm pack` and serves it from a loopback registry (`scripts/acceptance-server.mjs`, wired to the Worker through the operator-only `NPM_REGISTRY_URL` variable, https or loopback http only; tarballs must come from the same origin). Other package names, such as the `react` check, are proxied to registry.npmjs.org. The new case in `e2e/plugins.spec.ts` reviews `canopy-plugin-sample`, installs it, shows `Source: npm` provenance and runs the app in a native sandbox frame, on desktop and mobile. This is **local** evidence of the real tarball, SHA-512 integrity and import path. It is not evidence of an npm-published package.
